# 直播数据导出项目说明

本文档是项目的完整交接说明。新的开发任务或新的 Codex 窗口应先阅读本文档，再修改代码。

## 1. 项目目标

项目通过已登录的抖音公会后台，导出新心和中鼎两个后台指定自然日的直播数据，并生成适合日常查看的月度汇总。

最终需要四种业务数据：

1. 日数据：主播详情“直播数据 -> 数据详情”中的指定日指标。
2. 场次数据：在指定日期开播的所有直播场次。
3. 分钟数据：实际发生在指定自然日内的分钟明细。
4. 小时数据：由分钟明细按主播、自然小时聚合。

月度 Excel 只保存日、场次、小时三张汇总表。分钟明细使用 Parquet 单独保存，避免 WPS/Excel 因几十万或上百万行数据卡顿。

本项目与“AI 经纪人”项目相互独立，不包含主播视频录制、AI 分析、飞书或企业微信通知功能。

## 2. 当前状态

- 支持后台：新心、中鼎。
- 两个后台使用独立 Edge 登录态和独立调试端口。
- `data/` 与 `output/` 当前可以为空；首次导出会自动创建完整目录。
- Edge 登录态目录必须保留，否则需要重新登录。
- 主播名单缓存版本：`ANCHOR_CACHE_VERSION = 9`。
- 场次缓存版本：`SUMMARY_CACHE_VERSION = 8`。
- 分钟缓存版本：`MINUTE_CACHE_VERSION = 4`。

### 3.1 文件职责

| 文件 | 职责 |
| --- | --- |
| `app/browser.py` | 连接 Edge，并统一处理浏览器内请求队列、启动间隔、超时、并行任务和八轮重试 |
| `app/api.py` | 定义排行榜、主播详情、日趋势、场次和分钟接口，并把接口结果转换为业务数据 |
| `app/export.py` | 单后台单日导出、阶段控制、缓存、断点续跑、失败记录和 manifest |
| `app/report.py` | 字段映射、跨夜分钟筛选、小时聚合、CSV 和 Parquet 写入 |
| `app/combine_exports.py` | 合并双后台每日数据、按后台分组排序、生成月度 Excel |
| `app/browser_config.json` | 后台名称、调试端口、登录态目录和初始页面配置 |
| `app/start_edge.ps1` | 启动或复用指定后台的 Edge 调试窗口 |
| `app/run_all.ps1` | 双后台两阶段导出的总编排 |
| `app/run_range.ps1` | 按日期升序逐日调用单日流程，并在多日任务结束后统一刷新月汇总 |
| `START_EXPORT.cmd` | 日常一键导出入口 |
| `START_EDGE_*.cmd` | 单独打开某个后台的登录窗口 |

五个 Python 模块按浏览器请求、业务接口、导出编排、报表处理、月汇总分层。请求和重试只在 `browser.py` 实现一次，业务接口不再复制网络队列代码；不要为了减少文件数量把它们重新堆进一个文件。

## 4. 环境要求

- Windows 10/11。
- Python 3.11 或更高版本。
- Microsoft Edge。
- Python 依赖：`playwright`、`openpyxl`、`pandas`、`duckdb`。

首次安装：

```powershell
pip install -r requirements.txt
playwright install chromium
```

Playwright 不负责启动业务浏览器，只通过 CDP 连接已有 Edge；安装 Chromium 主要用于补全 Playwright 运行环境。

## 5. 双后台浏览器配置

配置文件：`app/browser_config.json`。

| 后台 | 配置键 | 调试端口 | 登录态目录 |
| --- | --- | --- | --- |
| 新心 | `xinxin` | `9223` | `.edge_debug_profile` |
| 中鼎 | `zhongding` | `9224` | `.edge_debug_profile_zhongding` |

两个登录态不能共用目录，否则浏览器会抢占配置文件或串登录状态。

首次运行或登录失效时：

1. 双击 `START_EDGE_新心.cmd`。
2. 在打开的 Edge 中登录新心后台。
3. 双击 `START_EDGE_中鼎.cmd`。
4. 在另一个 Edge 中登录中鼎后台。
5. 保持两个后台页面开启。

后续运行 `START_EXPORT.cmd` 会自动检查两个调试端口；端口未启动时会自动打开对应 Edge。

## 6. 一键运行

双击：

```text
START_EXPORT.cmd
```

程序会显示昨天作为默认开始日期，结束日期默认与开始日期相同：

```text
Start date, press Enter for yesterday [YYYY-MM-DD]:
End date, press Enter for the same day [YYYY-MM-DD]:
```

- 两次都直接回车：只导出昨天。
- 开始和结束都输入 `2026-07-01`：只导出 7 月 1 日。
- 开始输入 `2026-07-02`、结束输入 `2026-07-18`：依次导出 7 月 2 日至 7 月 18 日，包含首尾日期。
- 其他日期格式会被拒绝。

## 7. 完整执行流程

`START_EXPORT.cmd` 先调用 `app/run_range.ps1`。单日任务直接执行一次 `app/run_all.ps1`，完整顺序如下：

```text
检查/启动新心 Edge
-> 检查/启动中鼎 Edge
-> 新心日数据和场次
-> 中鼎日数据和场次
-> 刷新月日汇总和月场次汇总
-> 提示第一阶段完成
-> 新心分钟和小时
-> 中鼎分钟和小时
-> 刷新完整月汇总
-> 完成提示
```

第一阶段完成后，日数据和场次数据已经可用。分钟接口数量多，第二阶段会继续运行更长时间。

多日模式必须完整结束一天后才进入下一天，每天的数据、缓存和 manifest 仍分别写入各自日期目录。为了避免反复重写越来越大的 Excel，多日运行期间跳过每日月汇总，所有日期结束后再按涉及的月份各生成一次月汇总。某一天失败不会清除已完成缓存，程序会继续后续日期，并在最后列出失败日期。

## 8. 手动命令

在项目根目录执行。

连续导出一个日期范围：

```powershell
powershell -ExecutionPolicy Bypass -File .\app\run_range.ps1 -StartDate 2026-07-02 -EndDate 2026-07-18
```

只导出某后台的日和场次：

```powershell
python -m app.export --backend-name 新心 --date 2026-07-01 --phase summary
python -m app.export --backend-name 中鼎 --date 2026-07-01 --phase summary
```

在场次阶段完成后继续分钟和小时：

```powershell
python -m app.export --backend-name 新心 --date 2026-07-01 --phase minutes
python -m app.export --backend-name 中鼎 --date 2026-07-01 --phase minutes
```

单后台一次完成两个阶段：

```powershell
python -m app.export --backend-name 新心 --date 2026-07-01 --phase all
```

手动刷新月汇总：

```powershell
python -m app.combine_exports --month 2026-07
```

可调整分钟阶段参数：

```powershell
python -m app.export --backend-name 新心 --date 2026-07-01 --phase minutes --minute-interval-ms 150
```

正常使用优先运行 `START_EXPORT.cmd`，不要随意缩短请求间隔。

## 9. 后台接口

接口路径在 `app/api.py` 中集中定义：

| 数据 | 接口常量 | 用途 |
| --- | --- | --- |
| 主播排行榜 | `LEADERBOARD_API` | 通过自定义开始/结束日期获取指定历史单日名单，按音浪降序读取并保留音浪大于 0 的主播 |
| 主播分日趋势 | `DAILY_TREND_API` | 获取主播详情页“分日趋势图”的指定日指标 |
| 场次列表 | `ROOM_LIST_API` | 获取主播直播场次及场次汇总指标 |
| 分钟趋势 | `MINUTE_API` | 按 `roomID` 获取分钟趋势 |

请求通过后台页面中的 `fetch()` 发出，并携带当前页面登录态。项目不保存 Cookie、Token 或接口密钥到源码。所有单接口和多接口并行请求都复用 `app/browser.py` 中的同一套请求引擎，超时、临时错误识别和重试轮次不会在各业务接口中重复维护。

排行榜名单完成后，日趋势和场次列表在同一登录页面中作为两个独立任务并行请求。两类接口各自保持150毫秒启动间隔和独立重试，一类接口失败不会丢失另一类已完成的结果。

分钟接口依赖场次返回的 `roomID`，因此只能在场次请求完成后启动；小时数据再由分钟数据聚合。

排行榜返回的抖音号含字母时，程序会再读取主播详情中的 `short_id`，确保导出的 `抖音号/短ID` 为原始纯数字短 ID。

分钟接口一次只接受一个 `roomID`，不存在一次返回所有主播分钟数据的接口，因此分钟阶段是耗时最长的部分。

分钟结果以小批量从浏览器传回 Python，避免一次反序列化大量场次 JSON；同一导出进程复用一个 DuckDB 连接写入各主播 Parquet，减少重复初始化开销。PowerShell 直接显示 Python 输出，不再逐行二次转发。

## 10. 数据口径

以下规则是业务确认后的最终口径，修改前必须重新确认。

### 10.1 开播主播

所有日期统一使用排行榜的自定义日期查询（`rankType=5`），按 `income` 降序读取：

```text
income > 0
```

查询使用 `orderField=income&orderType=desc`，排行榜返回顺序就是当日音浪排名。程序逐页读取 `income > 0` 的主播；一旦当前页出现音浪为 0 的记录，就停止继续翻页。音浪为 0 的主播即使有开播时长也不进入名单，主播的 `liveDuration` 只作为附加信息保留，不再参与名单筛选。

### 10.2 日数据

- 日数据使用主播详情页“分日趋势图”接口。该接口与页面上方数据使用同一套已可见数据，不依赖当前返回空内容的“数据详情”表格接口。
- 不用场次数据反算。
- 跨夜导致的日指标归属以后台日接口为准。
- 单日查询缺少目标日记录时，自动改查30天范围并按日期精确取回，规避页面单日不显示但近30日可见的异常。
- 日表仅保留数据详情的实际字段，不再依赖更新较慢的主播数据大表。
- 每个后台的每日 CSV 保留该后台内部排名。

主要字段包括：总音浪、礼物音浪、活动音浪、道具音浪、订阅音浪、开播总时长、有效时长、平均在线、人气峰值及各直播类型音浪。

### 10.3 场次数据

为了找全目标日开播后跨到次日的场次，接口查询范围为目标日和次日。

场次最终归属规则：

```text
场次开播日期 == 目标日期
```

示例：

| 场次 | 是否进入 7 月 1 日场次表 |
| --- | --- |
| 6 月 30 日 23:00 -> 7 月 1 日 01:00 | 否，属于 6 月 30 日 |
| 7 月 1 日 10:00 -> 7 月 1 日 12:00 | 是 |
| 7 月 1 日 23:00 -> 7 月 2 日 02:00 | 是 |
| 7 月 2 日 00:30 -> 7 月 2 日 03:00 | 否 |

场次表保存整场汇总指标，不把跨夜场次拆成两条场次。

### 10.4 分钟数据

分钟和小时按自然日统计，与场次归属不同。

目标日分钟数据包含：

- 前一天开播并跨入目标日的目标日部分。
- 目标日开播并跨入次日的目标日部分。
- 目标日内普通场次的全部分钟。

仅保留：

```text
目标日 00:00:00 <= 分钟时间 <= 目标日 23:59:59
```

因此导出 7 月 1 日时：

- 6 月 30 日跨夜场次不进入 7 月 1 日场次表。
- 但该场次 7 月 1 日零点后的分钟必须进入 7 月 1 日分钟和小时数据。

### 10.5 小时数据

小时数据由目标自然日的分钟记录聚合，粒度为“主播 + 自然小时”。

主要规则：

- 数值型分钟指标求和。
- 平均在线人数取该小时分钟在线人数的平均值。
- 最高在线人数取该小时最大值。
- 直播间 ID 去重后拼接。
- `场次数` 是该主播该小时涉及的不同直播间数量。
- `开播时段秒（按开关播时间）` 是场次开关播区间与当前自然小时的交集秒数。

如果同一主播在同一小时开了两场，小时表会合并为一条主播小时记录，并在 `直播间ID` 和 `场次数` 中体现。

### 10.6 双后台月度分组排序

新心和中鼎每日 CSV 保留各后台内部排名，不再跨后台重新计算统一排名。

每个日期先完整展示新心，再展示中鼎；后台分组内部仍按各自的 `当日音浪排名` 排序。

月汇总排序：

- 月日汇总：日期升序、后台顺序（新心、中鼎）、后台内排名升序。
- 月场次汇总：开播日期升序、后台顺序、后台内排名升序、主播、开播时间升序。
- 月小时汇总：统计日期升序、后台顺序、后台内排名升序、主播、小时升序。

同一日期的新心和中鼎不能交替排列，同一主播的所有场次或小时必须连续展示。

## 11. 并发、间隔、超时和重试

默认参数：

| 类型 | 设置 |
| --- | --- |
| 场次接口并发 | 无固定上限，由请求数量决定 |
| 场次请求启动间隔 | 150 毫秒 |
| 日趋势接口并发 | 与场次接口同时运行 |
| 日趋势请求启动间隔 | 150 毫秒 |
| 分钟接口并发 | 无固定上限，由请求数量决定 |
| 分钟请求启动间隔 | 150 毫秒 |
| 单请求超时 | 60 秒 |

单个浏览器请求内部最多尝试 3 次，短等待为 1 秒、3 秒。

仍然失败时进入批量重试：

`HTTP 200` 但响应体为空也按临时失败处理，不会再作为 JSON 解析错误直接判死。

```text
第 1 轮失败 -> 等待 20 秒
第 2 轮失败 -> 等待 20 秒
第 3 轮失败 -> 等待 20 秒
第 4 轮失败 -> 等待 20 秒
第 5 轮失败 -> 等待 20 秒
第 6 轮失败 -> 等待 20 秒
第 7 轮失败 -> 等待 20 秒
第 8 轮仍失败 -> 记录最终失败
```

新的请求从第 1 轮重新开始，不会继承其他请求的失败次数。

以下错误被视为临时错误并重试：限频、服务器开小差、系统繁忙、请稍后重试、接口未返回、HTTP 429、超时、请求中止、`failed to fetch`、HTTP 5xx、`request failed`。

场次接口返回空列表时同样最多检查 8 轮，每轮之间等待 20 秒，避免把后台短暂空响应误判为场次缺失。

完成 8 轮检查后生成的场次缺失缓存会在续跑时直接复用，不会每次运行都重复等待 140 秒；缓存版本变更后才会重新确认。

### 11.1 为什么进度有时短暂停住

- 后台某些请求响应较慢。
- 单个请求正在内部短重试。
- 程序正在执行 20 秒重试冷却。
- 一个主播有多个直播间，必须等该主播所有房间完成后才更新一次主播进度。
- 剩余少量请求比平均请求慢。

只要后续进度继续增长，就不是死锁。超过 60 秒的单请求会被主动中止并进入重试，不会永久挂起。

如果旧版本运行中的进度长时间不动，同时命令窗口中有文字被选中，说明 Windows 控制台进入了文本选择状态。此时控制台会暂停程序的标准输出，程序可能阻塞在进度打印处；按 `Esc` 取消选择即可继续。当前版本启动时会关闭这种控制台暂停行为，并且分钟阶段只每完成 10 名主播或全部完成时打印一次进度，以减少控制台输出对性能的影响。

如果 Python 因未捕获异常退出，完整错误会保存到 `output/<后台>/<日期>/run_error.log`。重新运行成功后该日志会自动删除；因此日志存在表示该后台当天最近一次运行没有正常完成，可直接用它定位错误，不再依赖已经关闭的命令窗口。

## 12. 缓存和断点续跑

### 12.1 主播名单

```text
output/<后台>/<日期>/主播列表.json
```

同一天重新运行时自动复用，不需要额外参数。

### 12.2 场次缓存

```text
output/<后台>/<日期>/cache/summaries/<主播ID>.json
```

每完成一个主播立即保存，包含：

- 缓存版本和日期。
- 主播基础信息和日指标。
- 与目标自然日重叠、用于分钟请求的场次。
- 开播日期属于目标日的场次汇总行。

### 12.3 分钟/小时缓存

```text
output/<后台>/<日期>/cache/minutes/<主播ID>.json
```

包含该主播对应房间 ID、小时聚合结果和分钟行数。缓存只有在对应 Parquet 文件存在、日期和版本一致、房间列表一致时才有效。

重新运行时只请求缺失或失效的主播，不重复获取已完成数据。

不要手动只删除缓存或只删除 Parquet。需要彻底重跑某天时，应同时删除：

```text
data/<后台>/<日期>/
output/<后台>/<日期>/
```

## 13. 输出目录

### 13.1 分钟 Parquet

```text
data/<后台>/YYYY-MM-DD/anchor_id=<主播ID>/minutes.parquet
```

每个主播一个 Parquet，便于按日期和主播读取，也避免单文件过大。

### 13.2 每日输出

```text
output/<后台>/YYYY-MM-DD/
├─ 日汇总.csv
├─ 日数据失败记录.csv
├─ 场次汇总.csv
├─ 小时汇总.csv
├─ 主播列表.json
├─ manifest.json
├─ cache/
│  ├─ summaries/
│  └─ minutes/
├─ 场次失败记录.csv
├─ 场次缺失记录.csv
├─ 分钟小时失败记录.csv
└─ 无权限记录.csv
```

没有对应错误时，失败 CSV 不存在，不生成空文件。

CSV 使用 UTF-8 BOM 和标准 CRLF，一条数据一行。不要改回文本模式二次换行，否则 WPS 会显示隔行空白。

### 13.3 月度输出

```text
output/汇总/YYYY年MM月直播数据汇总.xlsx
```

工作簿包含：

- `月日汇总`
- `月场次汇总`
- `月小时汇总`

工作簿保持普通原始表格格式，不插入空行，不添加复杂样式。

## 15. 失败记录含义

### 场次失败记录

场次接口最终请求失败，例如持续限频、HTTP 5xx 或网络错误。

### 场次缺失记录

主播排行榜显示当天音浪大于 0，但查询目标日和次日后仍没有找到与目标日重叠的场次。它和接口失败是两种情况。

### 无权限记录

后台返回“用户没有权限”或主播已不属于当前公会。通常表示主播已经离开公会，不是程序故障。

### 分钟小时失败记录

至少一个场次的分钟接口最终失败，或者接口返回空分钟数据。该主播不会生成新的完整分钟缓存和小时结果，重新运行会继续请求。

## 16. 常见问题

### 没有找到已登录后台页面

确认对应 Edge 窗口已经打开并登录，页面 URL 位于 `union.bytedance.com/open/portal`，再重新运行。

### Edge 调试端口未就绪

关闭对应项目 Edge 窗口后重新运行 `START_EDGE_新心.cmd` 或 `START_EDGE_中鼎.cmd`。不要同时使用同一登录态目录启动多个 Edge。

### 接口临时失败

程序会自动最多尝试 8 轮，每轮之间等待 20 秒。偶发临时失败后恢复属于正常现象，不需要手工停止。

### 请求被限频

可把分钟间隔调大，例如：

```powershell
python -m app.export --backend-name 新心 --date 2026-07-01 --phase minutes --minute-interval-ms 800
```

### WPS 提示文件被占用

关闭正在打开的目标 CSV 或月度 Excel，再重新运行。程序不会强制关闭 WPS，以免丢失未保存内容。

### CSV 每条数据之间出现空行

当前代码已使用二进制方式写入标准 CRLF。若再次出现，检查 `app/report.py` 的 `write_csv()`，不要使用会对 `\n` 再次转换的文本写入方式。

### 月汇总新心和中鼎交替排列

检查 `app/combine_exports.py` 的后台排序键。每个日期必须先完整列出新心，再列出中鼎，并保留各后台自己的当日排名。

### 跨夜分钟缺失

检查场次查询是否同时覆盖目标日和次日，以及 `split_rooms()` 是否保留所有与目标自然日重叠的场次。场次表仍然只能保留目标日开播的场次。

## 17. 文件写入安全

JSON、CSV、Parquet、Excel 都先写临时文件，再替换正式文件。这样即使程序被中断，也尽量保留上一次完整结果。

- JSON 临时文件：`*.json.tmp`
- CSV 临时文件：`*.csv.tmp`
- Parquet 临时文件：`*.tmp.parquet`
- Excel 临时文件：`*.tmp.xlsx`

正常完成后不会残留临时文件。

## 18. 修改代码时的约束

1. 不得把日数据改为由场次计算。
2. 不得把 6 月 30 日开播的跨夜场次归入 7 月 1 日场次表。
3. 不得删除该跨夜场次发生在 7 月 1 日的分钟和小时数据。
4. 月汇总不得把新心和中鼎交替排列，必须按新心、中鼎分组。
5. 不得把分钟明细写入月度 Excel。
6. 不得删除断点缓存后仍声称支持续跑。
7. 不得把两个 Edge 后台改为共用登录态目录。
8. 不得用会产生 `CRCRLF` 的文本写入方式保存 CSV。
9. 不得为了减少文件数量破坏当前四层模块边界。
10. 修改缓存结构时必须提升对应缓存版本。
